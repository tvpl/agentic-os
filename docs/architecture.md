# MordomoOS — Architecture

## Principles

1. **One canonical source.** Skills, routines, routers, connectors and settings
   are files; run history, memory index and metrics live in SQLite
   (`config/db/mordomo.db`, WAL). The UI is a window, never the store.
2. **Vendor neutrality.** The core knows nothing about any provider. Claude,
   Cursor and Codex implement one `AgentAdapter` interface and are selected per
   run, per skill, per routine, or as the default. Adding a provider means
   exporting a manifest + adapter and registering it in
   `apps/api/src/context.ts` — see [adapters-guide.md](adapters-guide.md).
3. **Compiled views, not divergent copies.** Provider-native files
   (`CLAUDE.md`, `AGENTS.md`, `.claude/skills/`, `.cursor/rules|commands`,
   `.agents/skills/`) are generated by the sync compiler from the canonical
   source, tracked in a hash manifest, backed up before overwrite, and
   conflict-gated when hand-edited. No symlinks → fully portable to Windows.
4. **Local only by default.** Fastify binds `127.0.0.1` (another machine is served over TLS only); a local token
   (timing-safe compare) + a loopback-only `Host` allowlist protect against
   CSRF/DNS rebinding; changing the bind address is an explicit approval.

## Runtime topology

```
┌────────────────────────────  mordomo start ───────────────────────────┐
│ apps/api (Fastify @127.0.0.1:port)                                    │
│  ├─ serves apps/command-centre/dist (token injected into index.html)  │
│  ├─ REST API (zod-validated, uniform error envelope) + SSE            │
│  │    ├─ /api/runs/:id/stream  per-run events (Last-Event-ID resume)  │
│  │    └─ /api/events           one feed over the engine's event bus   │
│  ├─ request log → logs/api.jsonl (redacted; no bodies)                │
│  ├─ RunManager ── state machine, concurrency + bounded queue,         │
│  │    timeouts, cancellation, retention, graceful shutdown            │
│  │    └─ AgentAdapter.execute() ── safeSpawn (argv, basename          │
│  │         allowlist + pinned path, process-group kill, 1 MiB capture │
│  │         cap) → claude -p / cursor-agent -p / codex exec, parsed    │
│  │         into normalized RunEvents                                  │
│  ├─ RoutineScheduler (croner) ── catch-up, protect, retries, history  │
│  ├─ MemoryIndexer ── transactional chunks → files + FTS5 + links      │
│  └─ SQLite (better-sqlite3, WAL, versioned migrations, online backup) │
└───────────────────────────────────────────────────────────────────────┘
```

Boot order: apply a staged restore if `config/restore-pending/` exists
(safety backup first) → open the DB → prune expired run events → mark runs
left `running`/`queued` as `interrupted` (sending SIGTERM to their recorded
process group when it is still a live provider process) → start the
scheduler (catch-up) → listen → write `run/server.pid`.

Shutdown (SIGTERM/SIGINT, or `mordomo stop`): stop accepting requests, cancel
active runs and wait up to 10 s for them (they end as `interrupted`), close
SSE channels, then close the DB. `unhandledRejection` is logged, never fatal.

### The API contract (v1)

- **Versioned path.** `/api/v1/<rest>` is the documented path; Fastify's `rewriteUrl`
  routes it to the handler registered as `/api/<rest>` (`apps/api/src/apiVersion.ts`). The
  unversioned `/api/<rest>` answers the same and carries `Deprecation: true` and
  `Link: </api/v1/<rest>>; rel="successor-version"`. `GET /api/v1/meta` names
  `apiVersion: 1`. The Command Centre (`apiUrl()` in `apps/command-centre/src/api.ts`) and
  the CLI's MCP clients call `/api/v1`.
- **One error shape.** Every status `>= 400` is
  `{ "error": { "code", "message", "issues"? }, "message" }` (the top-level `message`
  repeats the inner one for older clients); no `2xx` carries `ok: false`. Channel tests
  answer `409 channel_not_configured` or `502 channel_failed`.
- **Scopes and limits.** Every route declares who may call it (`config.scope`: `owner`, or the
  `monitor`/`content`/`run`/`approve` scope a paired device must hold); the table, the `?token=` rule, the
  stream tickets, the TLS rule for other machines and the attempt limits are described in
  [security.md](security.md#authentication).
- **One table of routes.** `API` in `@mordomo/contracts` (`contracts/src/api`) has one entry for every route under
  `/api`: method, path, scope, `params`/`query`/`body` schemas, a response schema per success status, the errors the
  route raises and the headers it sets. The server registers a route only through `bind(app, "<id>", handler)`
  (`apps/api/src/contract.ts`): the entry decides the method, the path and the access, the three request parts reach
  the handler already parsed (a part that fails answers `400 validation` before the handler runs), and the handler's
  return type is the union of the entry's success bodies. A route registered any other way, or an entry nobody bound,
  stops `buildServer`. The Command Centre calls a route by its key (`apiCall("GET /api/runs/:id", { params })`), with
  parameters, query, body and result typed by the same entry.
- **Responses are checked where it is cheap.** In development and in tests (`validateResponses`, default on for
  `NODE_ENV=test|development`, `MORDOMO_VALIDATE_RESPONSES=1|0` decides either way; off in the installed service) each
  JSON answer is checked against its entry: the status is declared, the body satisfies the schema as an OUTPUT type (a key with
  a default is mandatory on the wire: `wireSchema`) and names no key the schema does not, an error is a `(status, code)` the route or `COMMON_ERRORS` declares. A departure answers
  `500 response_contract_violation` and is logged without the body.
- **Route document.** `GET /api/v1/openapi.json` (authenticated) is an OpenAPI 3.1 document generated from the table
  (`apps/api/src/openapi.ts`): every route with its method, path, parameters, request body, the response of each
  success status, the error envelope for each documented error (`400`, `401`, `403`, `404`, `409`, `413`, `415`,
  `422`, `429`, ...), `security` and `x-mordomo-scope` (the only extension). A test validates it with
  `@apidevtools/swagger-parser` and checks real answers against its schemas; another refuses a route that has no
  schema.
- **Events are versioned per type.** Each event type has its own list of versions
  (`@mordomo/contracts`, `EVENT_VERSIONS`), the bus envelope is a union discriminated by `type` and `v`, and the frames
  of a run's stream carry `v`. A client ignores an unknown type or a version above the highest it knows
  (`classifyEvent`, at `@mordomo/contracts/events`, which does not pull in zod). The policy and the fields of every
  version are in [events.md](events.md), generated from the schemas.

The CLI (`apps/api/src/cli.ts`, `node:util.parseArgs`) drives the same
`AppContext` directly for setup/doctor/index/sync/run/backup/restore, and
manages the service via a pidfile that records pid, port, start time and a
per-boot token (a recycled PID is not mistaken for a live service). Exit
codes: 0 ok, 1 failure, 2 usage error.

## Contracts (`contracts/src`)

`@mordomo/contracts` holds what crosses the engine / API / UI boundary and depends on
zod only, so the browser can import it: the wire types (`RunRecord`, `RunEvent`,
`RunUsage`, `Approval`, `NotificationRecord`, `SessionRecord`, `ProviderCapabilities`,
`MetricsSample`), the settings schema (`SettingsSchema`), the write policy
(`writeDecision`, `PROFILES`; also at `@mordomo/contracts/policy`, without zod) and the
typed event map. Every event the bus emits is `{ id, type, ts, v, payload }`, with
`payload` typed by `OsEventMap[type]` and `v` the current version of that type; a payload whose shape
changes incompatibly adds a version to the type's list ([events.md](events.md)). The core re-exports these under the same names (the UI-only `BrainSettings`,
`MicroApp` and `DEFAULT_HUD` stay in the contract). `typetests/` holds compile-time
proofs (`npm run typecheck`).

What only the Command Centre reads and writes (theme preset, micro apps, layouts, HUD,
Second Brain view) is `UiPreferences`, stored in `config/ui-preferences.json` and served
by `GET`/`PUT /api/ui-preferences`; the engine stores it and never interprets it.
`settings.json` carries `version` (now 2): an older file is migrated on its first read
(`core/src/config/migrations.ts`, the original kept as `settings.json.v<n>.bak`), and a
file written by a newer version is never overwritten (`code: "settings_newer"`).

## Core modules (`core/src`)

| Module | Responsibility |
|---|---|
| `config/` | Zod `SettingsSchema`, atomic file store with an mtime-keyed cache and deep-merge `update()`, local token; a field that fails the schema reads as its default, the file is left alone and the original is kept in `settings.json.invalid` |
| `db/` | open + versioned SQL migrations (once, in an `EXCLUSIVE` transaction that re-reads the version after the lock), pre-migration snapshot (`VACUUM INTO`), `MigrationError` / `DbNewerVersionError` |
| `security/` | redaction, path containment (realpath), the safe-read primitive (`safeFs.ts`: the one way a path chosen by a request, a record, an index row or a link is read), id validation for file-backed stores, exclusion matcher, secret blocklist, profiles, approval store |
| `spawn/` | argv-only spawn, basename allowlist (one `SpawnPolicy` per engine) + optional pinned path, timeouts, kill-tree, bounded stdout/stderr capture, `--help` probing helpers |
| `agents/` | `AgentAdapter` types, shared streaming executor |
| `runs/` | `RunManager`: explicit state transitions (`queued → running → done / failed / cancelled / timed_out / interrupted`), bounded queue, `parent_run_id` for retries, JSONL logs (rotating, redacted), metrics, boot recovery, retention pruning |
| `events.ts` | the `EventBus` with a ring buffer (`run.*`, `routine.*`, `index.*`, `approval.*`, `settings.changed`, `backup.created`) behind `/api/events`; each engine owns one (`engine.events`), there is none of the process |
| `execution/` | `engine.execution`: start, follow, cancel and approve runs with the engine's rules (write policy, working folders, who asked, idempotency); the API and the CLI are its clients |
| `errors.ts` | `MordomoError` and the stable codes of the engine's rules; `EngineLockedError`, `RestoreInProgressError`, `PathAccessError` |
| `sdk.ts` / `index.ts` / `internal.ts` | `createEngine` and the public surface of `@mordomo/core` ([sdk.md](sdk.md)); `internal` is the rest, for the app and the adapter packages |
| `skills/` | catalog (frontmatter + SKILL.md + resources), thick detection, run-prompt builder |
| `memory/` | shared exclusion policy (user globs + hard directory blocklist + secret basenames + content-based binary detection), indexer, FTS5 search, graph + relation explanations, router generator + staleness check, safe preview |
| `routines/` | JSON store, croner scheduler, missed-run catch-up, retries as linked runs, timezone inheritance, quoted OS unit generation |
| `connectors/` | registry, credential-free MCP discovery, ranked auditor (max 3) |
| `sync/` | config compiler: plan → diff → backup → apply with per-file conflict approval |
| `backup.ts` / `backupManifest.ts` | online backup (`db.backup()`) sealed with `manifest.json` (SHA-256 per file), restore that verifies the staged copies against it, journals the install and is undone if its process dies, pre-restore safety backup, staged restore applied at boot, retention (`limits.backupRetention`) |
| `restoreLock.ts` | the restore lock (the lock of `config/run/restore.lock`, released by the kernel): exclusive for a restore, the undoing of a dead one and a staged restore; shared for a backup (all of it) and for an engine being built (until its database is open) |
| `ownerLock.ts` / `processIdentity.ts` | the owner lock of a home: process identity (pid + start time + boot id), stale-lock takeover serialised by the database, release by token; a lock that names this process and is held by an engine of it is not stale (a second engine on the same home in one process is refused) |

### The SDK and what an engine owns

`@mordomo/core` is the public surface (`createEngine`, `engine.execution`, `engine.events`, the provider contract and
the errors; [sdk.md](sdk.md)); `@mordomo/core/internal` is everything the app and the adapter packages are made of,
with no stability promise. The HTTP routes and the CLI start, cancel and approve runs only through `engine.execution`,
so the write policy, the working-folder rule, the asker rules and the idempotency receipts are applied once, in the
core.

An engine owns its event bus, its spawn policy (the executables its providers may run and the environment its probes
drop) and its caches; two engines in one process share none of it. What stays at module level is the closed list in
`tests/sdk.instances.test.ts` (C30), each item with its reason: the operating system's process-wide resources (POSIX
locks, child pids, the PATH), the owner locks this process holds, memos keyed by the bus or the database they belong to,
and one table filled at load.

## Adapters

Each adapter implements: `detect` (PATH lookup + `--version` + `--help` flag
probing), `authenticate` (presence checks only — never reads/prints
credentials), `listModels`, `validateConfig`, `buildInvocation`,
`execute` (async iterable of normalized `RunEvent`s), `healthCheck`.
Cancellation is owned by `RunManager` (abort signal → process-group kill),
not by the adapter. Adapters are rebuilt whenever settings change, so a new
`binaryPath` takes effect on the next run.

Read-only enforcement per provider:

| Provider | Read-only mechanism | Enforced? | Write mechanism |
|---|---|---|---|
| Claude Code | headless `default` permission mode (auto-denies) + allow-rule scoped to the run's artifacts dir (`Write(//abs/path/**)`, `Edit(…)`) + `Bash(rm:*)`/`Bash(sudo:*)` disallowed | yes (by the CLI) | `--permission-mode acceptEdits` |
| Codex | `--sandbox read-only` (run refused if the installed CLI lacks the flag) | yes (by the CLI) | `--sandbox workspace-write` |
| Cursor | no `--force` (changes not auto-applied) + a read-only instruction appended to the prompt | **no — prompt-level only**; `cursor-agent` has no sandbox flag, so a read-only Cursor run can still write if the model ignores the instruction | `--force` |

`bypassPermissions` / `danger-full-access` are never used.

Effort mapping: Claude → thinking-token budget env; Codex →
`model_reasoning_effort`; Cursor → declared unsupported. Flags are always
confirmed against the installed CLI before use.

## Data flow of a skill run ("the button")

1. `POST /api/skills/:slug/run` validates slug (strict id), provider, inputs
   and `cwd` (must resolve inside the home or an enabled indexed folder, outside the home's `config/` and `logs/`; the home itself is not a working directory, so no `cwd` means `<home>/workspace`).
2. `RunManager.create` inserts a `queued` run (prompt summary pre-redacted);
   the queue is bounded at 10 × `limits.maxConcurrentRuns`.
3. The run prompt tells the agent to **read the canonical SKILL.md** (and only
   the resources its router points to — progressive disclosure), write outputs
   to `artifacts/<runId>/`, and treat workspace content as data.
4. Adapter builds the invocation; safeSpawn streams events → DB + JSONL
   (redacted) + SSE (`/api/runs/:id/stream`, and `run.*` on `/api/events`).
5. On exit: artifacts dir is scanned, status (`done`, `failed`, `timed_out`,
   `cancelled`, `interrupted`), duration and exit code recorded; empty
   artifact dirs are removed.

## Future: always-on runner

The scheduler is already decoupled from the UI (it lives in the service), and
routines/skills/settings are plain files — syncable by Syncthing as-is. A VPS
runner is the same service started on another machine with `MORDOMO_HOME`
pointing at the synced folder. See `docs/vps-syncthing.md`. Nothing is
installed or exposed without explicit approval.
