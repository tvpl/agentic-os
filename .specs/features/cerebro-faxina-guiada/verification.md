2. **Surviving mutant: the undo trusts any `from` in the manifest.** I removed
   `!isInside(memory, from) || isInside(archive, from) ||` from `manifestEntries` (`core/src/memory/cleanupApply.ts:355`).
   All of `cleanup.apply`, `cleanup.contract`, `cleanup.layer` and `cleanup.move` stayed green (44/44). The builder's own
   decision (g) in checks.md (Handoff, batch B) says the undo answers `409 undo_conflict` in four cases: JSON it cannot
   read, `v` other than 1, an entry whose `from` is outside `memory/` (or inside the archive), and an entry whose `to` is
   outside its own folder. Only `v: 2` is proven (`tests/cleanup.apply.test.ts:443`). Without the guard, a hand-edited
   manifest can make the undo move an archived file to a `from` under `artifacts/cleanup/` or inside another archive. The
   move's scope (`homeReadScope(home, [memory, artifacts])`, `cleanupApply.ts:398`) still refuses a `from` outside
   `memory/` and `artifacts/` as `forbidden_path`, so the guard is defence in depth. It is a branch the build added and
   never made fail.
3. **Surviving mutant: step 1's "última mudança há D dias" is not read over the scope (flagged item 2).** The route is
   the one the plan names. Plan Flow 1 says "para 'última mudança há D dias', a linha mais recente do escopo por
   `GET /api/memory/search` sem palavras". The core does answer a query with no words with the newest rows,
   `ORDER BY f.mtime DESC` with today's policy applied (`core/src/memory/search.ts:108-120`). So the choice of route is
   faithful. The reading of "do escopo" is not, because the search's notion of a scope is not the cleanup's:
   - for `context=<id>`, the search filters by `contextMembership` alone (`apps/api/src/routes/memory.ts:143`,
     `apps/api/src/routes/contexts.ts:25-31`). The cleanup scope also takes `memory/notes/<id>/` (amendment 3,
     `core/src/memory/cleanup.ts:79-90`). So N counts the context's notes folder and D never reads it. A context whose
     `ok` paths are all gone gets no row at all, and the line falls back to "N arquivos" with no D
     (`apps/command-centre/src/brain/cleanup/CleanupWizard.tsx:463-465`);
   - for `dir=<path>`, the search matches `f.dir LIKE '<dir>%'` (`core/src/memory/search.ts:58-60`), a string prefix
     with no separator and no real path. So `<R>/projetos` also reads `<R>/projetos-antigo/`, the very sibling C7 rules
     out of the scope (`cleanup.ts:120` uses `isInside` on the real path).

   C54 asserts the sentence against a mock that ignores the query
   (`apps/command-centre/src/brain/cleanup/testkit.tsx:137-138`). I dropped the scope from the request
   (`CleanupWizard.tsx:417`) and 94/94 UI tests stayed green. The e2e C55 reads "há 0 dias" in a fresh home, where every
   file is new, so it cannot tell either. C54 is a precision gap: it never says which set D is the newest of.

   `writeWorkspaceFile`'s own refusal removal (`safeWrite.ts:149`). Builder note (h) says this call "is not one it lists";
